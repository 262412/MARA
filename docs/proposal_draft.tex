\begin{abstract}
MARA (Multimodal Agentic Retrieval and Answering) is a proposed local-first, controller-based, Self-RAG-inspired framework for multimodal document question answering. Instead of using one fixed RAG pipeline, MARA will use an agent controller to decide whether to answer directly, retrieve text, retrieve page images, retrieve document elements, use a GraphRAG route, combine several routes, verify evidence, retry, or abstain. The prototype will combine a shared Web/CLI runtime, multimodal evidence bundles, citation-aware answers, page preview, route traces, guardrails and a benchmark harness for evaluating answer quality, citation quality and hallucination risk.
\end{abstract}

\section{Project Description}

MARA will help users search, compare and understand mixed document collections through a web workbench and command-line workflow. The project is now framed as a hybrid multimodal RAG system controlled by an agent controller. The controller receives a \texttt{DocQARequest}, chooses one or more routes, executes retrieval, evaluates evidence quality, generates or rejects an answer, and returns a \texttt{DocQAResponse} with citations, evidence and trace metadata.

The phrase ``Self-RAG-inspired'' is used deliberately. MARA will not train a new language model with Self-RAG reflection tokens. Instead, the control semantics of Self-RAG will be externalised into program-level decisions: route selection, retrieval decisions, evidence evaluation, claim verification, retry, rewrite and abstention. This keeps the thesis feasible while preserving the central research question: can an agent controller improve document QA by choosing the right RAG route and refusing weak evidence?

The main routes will be \texttt{direct\_answer}, \texttt{text\_rag}, \texttt{page\_image\_rag}, \texttt{element\_rag}, \texttt{graph\_rag}, \texttt{hybrid\_rag} and \texttt{abstain}. Text RAG will use existing chunk and vector retrieval. Page-image RAG will add a ColPali-style visual page retrieval interface. Element RAG will retrieve tables, figures, formulas and slide/page elements. GraphRAG will be a specialist route for global summaries, cross-document comparison and ``connect the dots'' questions, not the default factual QA path.

The first engineering priority is to control system debt. The existing code already has Web and CLI entry points, local state, preview, knowledge map, artifact and benchmark scaffolding. These are useful, but they also create boundary risk: a large chat page, UI/runtime coupling, Web/CLI drift, thick dependencies and immature notebook/PPTX workflows. The proposal therefore prioritises a smaller researchable system: shared runtime contracts, route/executor registries, evidence schema, controller trace, benchmark harness and a thin UI adapter.

\section{Aims and Requirements}

The aims of the project are:

\begin{itemize}
  \item To design and implement a local-first, controller-based hybrid RAG framework for multimodal document question answering.
  \item To investigate whether a Self-RAG-inspired controller can choose between direct answering, text RAG, page-image RAG, element RAG, GraphRAG, hybrid retrieval and abstention.
  \item To improve answer reliability through evidence bundles, page/element citations, CRAG-style retrieval evaluation, claim verification and traceable route decisions.
  \item To evaluate the system with route-level ablations and ALCE/MMDocRAG/RAGTruth-style metrics for answer quality, citation quality, multimodal evidence support and hallucination risk.
\end{itemize}

\textbf{Essential requirements:}
\begin{itemize}
  \item Users can upload and index PDF, Word, PowerPoint, Excel/CSV, Markdown and plain-text files.
  \item Users can ask questions over all indexed documents or selected files.
  \item Web and CLI requests pass through one shared DocQA runtime rather than duplicating route or session logic.
  \item The system defines stable \texttt{RouteDecision}, \texttt{RetrieveDecision}, \texttt{EvidenceBundle}, \texttt{VerifyDecision} and \texttt{ControllerTrace} contracts.
  \item A route registry and executor registry support \texttt{direct\_answer}, \texttt{text\_rag}, \texttt{page\_image\_rag}, \texttt{element\_rag}, \texttt{graph\_rag}, \texttt{hybrid\_rag} and \texttt{abstain}.
  \item The indexing layer supports text chunks, page-image records, element records and graph records with source back-references.
  \item The controller selects routes, records reasons, respects allowed routes, and handles invalid planner output through a safe fallback or abstention.
  \item A CRAG-style retrieval evaluator classifies retrieved evidence as good, ambiguous or poor before generation.
  \item The claim verifier labels generated claims as supported, unsupported or not enough evidence, then triggers revise, retry or abstain when needed.
  \item Answers include page-level, slide-level, element-level or graph-level citations and expose a compact execution trace.
  \item The benchmark compares fixed text RAG, individual routes, controller-auto routing, hybrid retrieval and CRAG-guarded execution.
  \item Automated tests cover controller decisions, route executors, evidence schemas, Web/CLI contracts, benchmark metrics and important UI services.
\end{itemize}

\textbf{Desirable requirements:}
\begin{itemize}
  \item A configurable ColPali or VLM backend for real page-image retrieval and visual answering; if unavailable, the benchmark must label the backend as local smoke or not configured.
  \item A trainable or learnable router inspired by Adaptive-RAG or MAO-ARAG after enough controller traces have been collected.
  \item Richer graph interaction, such as full-screen pan, zoom, filtering and study-guide views.
  \item Stable artifact generation beyond outlines, such as PPTX generation, only after the core controller and benchmark are reliable.
\end{itemize}

\section{Key Literature and Background Reading}

RAG grounds language models in external evidence, but a fixed retrieve-then-generate pipeline is not always appropriate \cite{lewis2020rag, gao2023rag}. Some questions can be answered directly, some need text chunks, some need visual page evidence, some need table or figure elements, and some require global graph summaries. Self-RAG shows that retrieval and critique can be made adaptive through reflection tokens \cite{asai2023selfrag}. MARA will not train such tokens; it will implement their control meaning as explicit controller fields and guardrail states.

Adaptive-RAG and MAO-ARAG support the routing part of the design. Adaptive-RAG selects strategies according to query complexity using a trained classifier \cite{jeong2024adaptiverag}. MAO-ARAG uses a planner agent to select executor agents and optimise answer quality under cost constraints \cite{chen2025maoarag}. These works motivate a future learnable router, but MARA's first version will use a local heuristic or LLM planner with structured JSON output and trace logging.

CRAG is relevant because it treats retrieval quality as a first-class problem. Its retrieval evaluator judges retrieved documents and triggers corrective actions when evidence is weak \cite{yan2024crag}. MARA will adapt this idea as a controller guardrail: evidence is evaluated before generation, and poor or ambiguous evidence can cause retry, route switch or abstention.

For multimodal and multi-page documents, M3DocRAG shows that document QA benefits from multimodal retrieval across pages and documents rather than relying only on OCR text \cite{cho2024m3docrag}. ColPali further motivates direct page-image retrieval using visual document embeddings and late interaction \cite{faysse2024colpali}. MARA will therefore use a hybrid index: text chunks, page-image records and element records, instead of replacing text extraction with a purely visual route.

GraphRAG addresses a different class of question: global sensemaking over a corpus. It builds an entity graph and community summaries to answer query-focused summarisation questions that conventional top-k RAG handles poorly \cite{edge2024graphrag}. MARA will use GraphRAG as a specialist route for summaries, comparisons, study guides and relationship exploration, while preserving page or element citations whenever possible.

Evaluation will be based on systems that make citation and multimodal grounding measurable. ALCE evaluates end-to-end cited generation using fluency, correctness and citation quality \cite{gao2023alce}. MMDocRAG provides a multimodal document QA benchmark focused on evidence selection across text, images and tables \cite{dong2025mmdocrag}. RAGTruth provides hallucination annotations for RAG outputs and is useful for unsupported-claim detection \cite{niu2024ragtruth}. MARA's benchmark will combine these ideas into route-level ablations and reliability metrics.

The user interface remains important because the system must expose evidence rather than hide it. Gradio supports a Python-first workbench with upload, chat, preview and settings components \cite{gradioDocs}. OWASP guidance highlights LLM risks such as prompt injection and sensitive information disclosure \cite{owaspLLM}; MARA will mitigate these through local-first storage, clear backend metadata, no hidden web access and benchmark-visible trace records.

\section{Development and Implementation Summary}

The project will be implemented mainly in Python 3.10+. The repository has three main layers: \texttt{kotaemon} for LLM wrappers, loaders, vector stores and retrieval; \texttt{ktem} for the Gradio app runtime, settings, preview and DocQA orchestration; and \texttt{slide-cli} as the internal package exposing the public \texttt{MARA} CLI. The new architecture will keep this separation but move controller logic into shared runtime/services so that Web and CLI cannot drift.

Development will begin by freezing system boundaries. The chat page will not continue to absorb business logic; Web UI code should construct requests and render responses, while controller execution, evidence construction, graph context and benchmark reporting live in focused services. Non-core or unstable features such as full PPTX generation and richer notebook workflow will be treated as disabled or deferred if they distract from the research prototype.

\textbf{Controller workflow:}
\begin{enumerate}
  \item Convert Web or CLI input into a \texttt{DocQARequest}.
  \item Use a heuristic or LLM planner to select routes and write a \texttt{RouteDecision}.
  \item Execute one or more route executors and return a unified \texttt{EvidenceBundle}.
  \item Run a CRAG-style evaluator before generation; poor evidence triggers retry, route switch or abstain.
  \item Generate an answer only from accepted evidence and record citations.
  \item Run claim verification; unsupported or insufficient evidence triggers one rewrite, retry or abstention.
  \item Return answer text, citations, route trace, evidence metadata, backend metadata and verification result.
\end{enumerate}

\section{Data Sources}

The project will use public, open-licence, synthetic or self-created documents such as papers, technical documentation, generated reports, screenshots and slides. These will be used only where permitted and cited if they appear in the dissertation. The application may also process self-provided non-sensitive test files during development. Self-created screenshots and slides will avoid personal, confidential or copyrighted third-party content unless permission is clear.

The benchmark will contain public or synthetic multimodal documents and manually prepared question-answer pairs. Each item will include the query, expected route or route family, target modality, expected answer, accepted evidence references, and source identifiers such as file name, page, slide, table, figure, bounding box, element ID or graph community. Predictions will also record backend metadata so that local smoke backends are not confused with configured ColPali, VLM or LLM-planner backends. No private scraping, personal records, confidential documents or participant feedback are required.

\section{Testing and Evaluation}

Technical testing will cover controller schema validation, route selection, route executors, evidence bundle construction, retrieval evaluation, claim verification, citation construction, CLI commands, Web/CLI contract behaviour, knowledge graph services and benchmark metrics. Integration tests will check that a document or slide deck can be indexed, routed, retrieved, answered, verified and cited through the same runtime used by both Web and CLI.

The evaluation will use route-level ablations. The main comparison will include fixed text RAG, direct answer, text RAG, page-image RAG, element RAG, local/global GraphRAG, hybrid RAG, controller-auto routing and CRAG-guarded execution. Each benchmark item will record the expected answer, expected route or evidence type, acceptable evidence, and the page, slide, element, image region or graph community that justifies it.

Metrics will combine several evaluation traditions. ALCE-style metrics will report fluency, correctness, citation precision/recall and attributable claim rate. MMDocRAG-style metrics will report page hit, element hit, image quote hit, cross-page evidence hit and multimodal answer support. RAGTruth-style metrics will report unsupported claim count, unsupported claim rate, contradiction count and abstention correctness. The benchmark will also report routing accuracy, retrieval recall@k/MRR, latency, backend type, cost where relevant, and qualitative error categories.
