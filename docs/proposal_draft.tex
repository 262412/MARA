\begin{abstract}
MARA is a multimodal agentic retrieval and answering framework for searching, summarising and exploring collections of documents in multiple formats. The LLM agent will plan different workflows based on different documents, select appropriate tools, look for evidence from text, page or slide structure, tables and limited OCR/image derivative content, and then generate a cited response. This prototype integrates features such as multimodal information processing, RAG, citation review, page preview, and knowledge graph into the Web and CLI.
\end{abstract}

\section{Project Description}

MARA will help users search and understand mixed document collections through a web interface and command-line workflow. Here, ``multimodal'' means text, page or slide structure, tables and a scoped OCR/image adapter for selected figures, screenshots or scanned regions. ``Agentic'' behaviour will be defined as query classification, tool selection, multi-step execution and logged tool-use decisions, rather than only using an LLM to write the final answer.

The project builds on the existing Python repository, a fork of Kotaemon/Slides, and extends its retrieval-augmented generation (RAG), page preview, citation review and knowledge graph features. Users will upload PDFs, Word files, slides, spreadsheets, Markdown and text files, index them locally, then ask natural-language questions. MARA will retrieve evidence, generate a cited answer, and let the user inspect the original page, slide, table or image-derived source.

Ordinary file search is weak for complex documents, while generic chatbots may answer without showing sources. MARA therefore combines conversation with visible evidence and a lightweight tool-use trace. The application will look like a research workbench: file index, chat area, preview panel, tool trace and knowledge graph. Graph nodes will represent documents, pages or slides, entities/topics and cited evidence; edges will represent containment, citation, co-occurrence or follow-up relations.

\section{Aims and Requirements}

The aims of the project are:

\begin{itemize}
  \item To design and implement a local multimodal agentic framework for question answering, summarisation and knowledge exploration across documents, slides, tables and scoped visual/OCR evidence.
  \item To investigate how an LLM agent can classify queries, select tools, plan multi-step workflows, and produce evidence-grounded answers.
  \item To improve transparency by linking generated answers to retrieved evidence, page or slide previews, citation review and a lightweight knowledge graph.
  \item To evaluate whether the system meets representative practical requirements for multimodal document exploration.
\end{itemize}

\textbf{Essential requirements:}
\begin{itemize}
  \item Users can upload and index PDF, Word, PowerPoint, Excel/CSV, Markdown and plain-text files.
  \item Users can ask questions over all indexed documents or selected files.
  \item The system extracts and indexes text, metadata, page or slide structure and table evidence from supported files, with scoped OCR/image-derived evidence for selected visual content where available.
  \item The LLM agent classifies queries, selects tools, executes multi-step workflows, and logs tool-use decisions.
  \item The system retrieves relevant evidence and generates answers with citations.
  \item Users can open cited sources in a preview panel and inspect page-level, slide-level, table or image-derived evidence.
  \item Conversations and indexes are persisted locally so the web UI and CLI can share the same runtime state.
  \item The interface shows enough agent/tool state to make the tool-use trace inspectable.
  \item The evaluation includes a text-only RAG baseline using the same benchmark queries.
  \item The project includes automated tests for multimodal ingestion, tool routing, retrieval, citation handling, CLI behaviour and important UI services.
\end{itemize}

\textbf{Desirable requirements:}
\begin{itemize}
  \item Local-model support for privacy-sensitive use cases.
  \item Richer graph interaction, such as full-screen pan, zoom and node filtering.
\end{itemize}

\section{Key Literature and Background Reading}

The technical basis is retrieval-augmented generation. Lewis et al. describe RAG as combining a language model with an external knowledge source, so answers can be grounded in retrieved passages rather than model memory alone \cite{lewis2020rag}. Dense passage retrieval embeds questions and passages into a shared vector space \cite{karpukhin2020dpr}. Recent surveys show that RAG can improve grounding, but retrieval quality, chunking and evaluation remain difficult \cite{gao2023rag}. MARA therefore exposes retrieved evidence, citations and page preview, and evaluates retrieval separately from generation.

The agentic part is informed by work on reasoning and tool use. ReAct shows that language models can interleave reasoning with actions \cite{yao2022react}, while Toolformer demonstrates external tool calls \cite{schick2023toolformer}. MARA applies this through query classification, tool selection, multi-step execution, and logged decisions for text retrieval, slide-aware retrieval, OCR/image extraction, citation lookup or graph exploration.

The multimodal part is motivated by image-text and document AI work. CLIP aligns visual and textual representations \cite{radford2021clip}; LayoutLMv3 combines text, layout and visual signals for document understanding \cite{huang2022layoutlmv3}. These ideas justify treating documents as more than plain text when answers depend on layout, figures or slide structure.

The UI matters because users must inspect sources, not just receive answers. Gradio supports Python-first upload, chat, preview and settings components \cite{gradioDocs}, which fits the workbench design. OWASP guidance highlights LLM risks such as sensitive information disclosure and prompt injection \cite{owaspLLM}; MARA will reduce these risks through local storage, minimal personal data use and public or synthetic test data.

\section{Development and Implementation Summary}

The project will be implemented mainly in Python 3.10+. The repository has three main layers: \texttt{kotaemon} for LLM wrappers, loaders, vector stores and retrieval; \texttt{ktem} for the Gradio app runtime, settings, preview and DocQA orchestration; and \texttt{slide-cli} for the public \texttt{slide} CLI. This separates core RAG logic, services and user-facing commands.

Development will begin with reading and code review, then progress through multimodal ingestion, tool routing, cited answers, preview, knowledge graph interaction and UI polish. Targeted tests, Git and a short development log will support project management.

The main workflow will be:
\begin{enumerate}
  \item Load documents through the web UI or CLI.
  \item Extract text, metadata, page or slide structure, table content, and scoped OCR/image-derived descriptions.
  \item Split the extracted content into retrievable units and store them in document and vector stores.
  \item Receive a user query and let the LLM agent classify the task, plan steps, and select tools.
  \item Run selected retrieval, preview, summarisation, comparison, citation-checking or graph tools.
  \item Generate an answer from multimodal evidence and tool outputs.
  \item Display the answer, citations, evidence cards, preview links and concise tool-use trace.
  \item Build or refresh a conversation knowledge graph for follow-up exploration.
\end{enumerate}

\section{Data Sources}

The project will use public, open-licence, synthetic or self-created documents such as papers, technical documentation, generated reports, screenshots and slides. These will be used only where permitted and cited if they appear in the dissertation. The application may also process self-provided non-sensitive test files during development.Self-created screenshots and slides will avoid personal, confidential or copyrighted third-party content unless permission is clear.

The evaluation will use a fixed benchmark of public or synthetic multimodal documents and manually prepared question-answer pairs. Each item will include a query, target modality, expected answer, accepted evidence references, and source identifiers such as file name, page, slide, table, figure or image region. No private scraping, personal records, confidential documents or participant feedback are required.

\section{Testing and Evaluation}

Technical testing will cover document parsing, multimodal extraction adapters, indexing, agent tool routing, retrieval, citation construction, CLI commands and knowledge graph services. Integration tests will check that a document or slide deck can be indexed, queried and cited. Manual UI testing will verify upload, chat, preview, citation navigation, graph generation and tool-use trace display.

Evaluation will use representative tasks: document QA, slide summarisation, table or figure questions, cross-document comparison and citation lookup. Ground truth will be manually annotated from the sources, recording the expected answer, expected tool type, acceptable evidence, and the page, slide, table or visual region that justifies it. MARA will be compared with a simple text-only RAG baseline using the same benchmark queries. Measures will include retrieval recall@k and MRR; routing accuracy against the labelled expected tool; citation support as the proportion of answer claims supported by accepted evidence; answer faithfulness using a manual rubric; optional LLM-assisted scoring may be used only as a secondary aid and will be checked manually.; benchmark item success rate; latency and cost; and qualitative error analysis.

\section{Project Ethics and Human Participants}

No human participants or beta testers are planned. Evaluation will use technical tests and benchmark tasks built from public, synthetic or self-provided non-sensitive documents. No recruitment, interview, survey, observation or personal feedback data will be collected. If I later add a user study, I will update the ethics statement and check with my supervisor first.
