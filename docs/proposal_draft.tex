\begin{abstract}
MARA (Multimodal Agentic Retrieval and Answering) is a proposed local-first, controller-based framework for multimodal document question answering, inspired by Self-RAG’s idea of deciding when to retrieve, verify, retry or abstain. Instead of using one fixed RAG pipeline, MARA will use an agent controller to decide whether to answer directly, retrieve text, retrieve page images, retrieve document elements, use a GraphRAG route, combine several routes, verify evidence, retry, or abstain. The prototype will combine a shared Web/CLI runtime, multimodal evidence bundles, citation-aware answers, page preview, route traces, guardrails and a benchmark harness for evaluating answer quality, citation quality and hallucination risk.
\end{abstract}

\section{Project Description}

MARA will help users search, compare and understand mixed document collections through a web workbench and command-line workflow. The project is now framed as a hybrid multimodal RAG system controlled by an agent controller. The controller receives a \texttt{DocQARequest}, chooses one or more routes, executes retrieval, evaluates evidence quality, generates or rejects an answer, and returns a \texttt{DocQAResponse} with citations, evidence and trace metadata.

The phrase ``Self-RAG-inspired'' is used deliberately. MARA will not train a new language model with Self-RAG reflection tokens. Instead, the control semantics of Self-RAG will be externalised into program-level decisions: route selection, retrieval decisions, evidence evaluation, claim verification, retry, rewrite and abstention. This keeps the thesis feasible while preserving the central research question: can an agent controller improve document QA by choosing the right RAG route and refusing weak evidence?

The main routes will be \texttt{direct\_answer}, \texttt{text\_rag}, \texttt{page\_image\_rag}, \texttt{element\_rag}, \texttt{lightweight\_graph\_rag}, \texttt{hybrid\_rag} and \texttt{abstain}. Text RAG will use existing chunk and vector retrieval. Page-image RAG will provide a ColPali-style route interface using page-image records, with real ColPali or VLM backends treated as configurable extensions if available. Element RAG will retrieve tables, figures, formulas and slide/page elements. GraphRAG will be a specialist route for global summaries, cross-document comparison and ``connect the dots'' questions, not the default factual QA path.

The first engineering priority is to control system debt. The existing code already has Web and CLI entry points, local state, preview, knowledge map, artifact and benchmark scaffolding. These are useful, but they also create boundary risk: a large chat page, UI/runtime coupling, Web/CLI drift, thick dependencies and immature notebook/PPTX workflows. The proposal therefore prioritises a smaller researchable system: shared runtime contracts, route/executor registries, evidence schema, controller trace, benchmark harness and a thin UI adapter.

\section{Aims and Requirements}

The aims of the project are:

\begin{itemize}
  \item To design and implement a local-first, controller-based hybrid RAG framework for multimodal document question answering.
  \item To investigate whether a Self-RAG-inspired controller can choose between direct answering, text RAG, page-image RAG, element RAG, GraphRAG, hybrid retrieval and abstention.
  \item To improve answer reliability through evidence bundles, page/element citations, CRAG-style retrieval evaluation, claim verification and traceable route decisions.
  \item To evaluate the system with route-level ablations and ALCE/MMDocRAG/RAGTruth-style metrics for answer quality, citation quality, multimodal evidence support and hallucination risk.
\end{itemize}

\textbf{Scope note:} in this proposal, ``essential'' means a stable controller interface, simplified but working route implementations, and a benchmark harness that can compare those routes. It does not mean a production-level reproduction of Self-RAG, CRAG, ColPali, GraphRAG or MMDocRAG. Full visual-language backends, full GraphRAG engineering and trainable routing are configurable or scoped extensions.

\textbf{Essential requirements:}
\begin{itemize}
  \item Users can upload, index and query PDF, Word, PowerPoint, Excel/CSV, Markdown and plain-text files through the shared Web/CLI DocQA runtime.
  \item The system defines stable \texttt{RouteDecision}, \texttt{RetrieveDecision}, \texttt{EvidenceBundle}, \texttt{VerifyDecision} and \texttt{ControllerTrace} contracts.
  \item A route and executor registry supports \texttt{direct\_answer}, \texttt{text\_rag}, \texttt{page\_image\_rag}, \texttt{element\_rag}, \texttt{lightweight\_graph\_rag}, \texttt{hybrid\_rag} and \texttt{abstain}.
  \item The prototype implements simplified, benchmarkable versions of \texttt{text\_rag}, controller-auto routing and at least one multimodal route, while clearly labelling any smoke or unavailable backend.
  \item The indexing layer stores text chunks, page-image records, element records and lightweight graph records with source back-references.
  \item The controller selects routes, records reasons, respects allowed routes, and handles invalid planner output through a safe fallback or abstention.
  \item Lightweight CRAG-style retrieval evaluation and claim verification decide whether to generate, retry, revise or abstain.
  \item Answers include citations, evidence metadata and a compact execution trace that can be inspected in the UI and benchmark output.
  \item The benchmark harness compares fixed text RAG, selected route executors, controller-auto routing, hybrid retrieval and guarded execution.
  \item Automated tests cover controller decisions, route executors, evidence schemas, Web/CLI contracts, benchmark metrics and important UI services.
\end{itemize}

\textbf{Desirable requirements:}
\begin{itemize}
  \item A configurable ColPali or VLM backend for real page-image retrieval and visual answering; otherwise, page-image RAG will use local page-image records or smoke backends clearly labelled in benchmark reports.
  \item A trainable or learnable router inspired by Adaptive-RAG or MAO-ARAG after enough controller traces have been collected.
  \item Richer graph interaction, such as full-screen pan, zoom, filtering and study-guide views.
  \item Stable artifact generation beyond outlines, such as PPTX generation, only after the core controller and benchmark are reliable.
\end{itemize}

\section{Key Literature and Background Reading}

The main background idea is RAG: instead of asking a language model to answer only from memory, the system first retrieves relevant source material and then asks the model to answer using that evidence \cite{lewis2020rag}. Dense Passage Retrieval is one influential way to find relevant passages by embedding questions and passages into a shared vector space \cite{karpukhin2020dpr}. Recent surveys show that this evidence-grounded pattern is useful but still difficult to evaluate and control \cite{gao2023rag}. This matters for document QA because the answer can be linked back to pages, slides, tables or other sources. A simple RAG system usually follows one fixed path: retrieve text chunks, generate an answer, then show citations. MARA starts from this idea but asks whether the system can choose a better path for different types of question.

Self-RAG is important because it treats retrieval as a decision rather than a fixed step \cite{asai2023selfrag}. In plain terms, Self-RAG asks: should the system retrieve anything, is the retrieved evidence relevant, does the answer really follow from it, and is the final answer useful? The original paper trains a model to make these decisions with special reflection tokens. MARA will not train that kind of model. It will use Self-RAG as design inspiration and implement the same decisions as explicit controller fields, logs and guardrail states.

Adaptive-RAG and MAO-ARAG help explain the routing problem \cite{jeong2024adaptiverag, chen2025maoarag}. Some questions are easy and only need a direct answer; others need document retrieval, visual evidence, graph summaries or several routes together. These papers motivate routing as a research problem in its own right. In this project, the first router will be a heuristic or structured LLM planner. A trainable router is treated as future work after enough route traces have been collected.

CRAG focuses on a practical failure mode: if the retrieval step finds weak or irrelevant evidence, the generated answer is likely to be wrong \cite{yan2024crag}. CRAG therefore uses a retrieval evaluator before generation. MARA will use a simplified version of this idea. Retrieved evidence will be labelled good, ambiguous or poor. Good evidence can be used for generation; ambiguous evidence can trigger retry or hybrid fallback; poor evidence can trigger route switching or abstention.

M3DocRAG and ColPali motivate the multimodal document side of the project \cite{cho2024m3docrag, faysse2024colpali}. Many documents are not just plain text: answers may depend on page layout, a figure, a table, a formula, or content spread across several pages. M3DocRAG supports multi-page and multi-document retrieval, while ColPali shows that directly retrieving page images can preserve visual details that OCR text may lose. MARA will use these ideas at prototype scale through a hybrid index of text chunks, page-image records and element records. It will not claim production-level ColPali or VLM performance unless those backends are configured and evaluated.

GraphRAG is useful for questions about the whole collection rather than one page \cite{edge2024graphrag}. For example, a user might ask for the main themes across a set of papers or how several concepts are connected. GraphRAG builds an entity graph and community summaries for this kind of global question. MARA will implement a lightweight graph route for summaries, comparisons and ``connect the dots'' tasks. It will not make GraphRAG the default path for ordinary page-specific questions.

The evaluation literature explains how the project will measure success. ALCE evaluates whether cited generated answers are fluent, correct and well supported by citations \cite{gao2023alce}. MMDocRAG focuses on multimodal document QA and evidence selection across text, images and tables \cite{dong2025mmdocrag}. RAGTruth provides labels for hallucination and unsupported claims in RAG outputs \cite{niu2024ragtruth}. MARA will adapt these ideas into a smaller thesis benchmark, using route-level ablations and metrics such as citation quality, multimodal evidence support and unsupported claim rate, rather than trying to reproduce the full external benchmarks.

The user interface remains important because the system must expose evidence rather than hide it. Gradio supports a Python-first workbench with upload, chat, preview and settings components \cite{gradioDocs}. OWASP guidance highlights LLM risks such as prompt injection and sensitive information disclosure \cite{owaspLLM}; MARA will mitigate these through local-first storage, clear backend metadata, no hidden web access and benchmark-visible trace records.

\section{Development and Implementation Summary}

The project will be implemented mainly in Python 3.10+. It builds on a Kotaemon-style document QA baseline \cite{kotaemon}. The repository has three main layers: \texttt{kotaemon} for LLM wrappers, loaders, vector stores and retrieval; \texttt{ktem} for the Gradio app runtime, settings, preview and DocQA orchestration; and \texttt{slide-cli} as the internal package exposing the public \texttt{MARA} CLI. The new architecture will keep this separation but move controller logic into shared runtime/services so that Web and CLI cannot drift.

Development will begin by freezing system boundaries. The chat page will not continue to absorb business logic; Web UI code should construct requests and render responses, while controller execution, evidence construction, graph context and benchmark reporting live in focused services. Non-core or unstable features such as full PPTX generation and richer notebook workflow will be treated as disabled or deferred if they distract from the research prototype.

\textbf{Controller workflow:}
\begin{enumerate}
  \item Convert Web or CLI input into a \texttt{DocQARequest}.
  \item Use a heuristic or LLM planner to select routes and write a \texttt{RouteDecision}.
  \item Execute one or more route executors and return a unified \texttt{EvidenceBundle}.
  \item Run a CRAG-style evaluator before generation; poor evidence triggers retry, route switch or abstain.
  \item Generate an answer only from accepted evidence and record citations.
  \item Run claim verification; unsupported or insufficient evidence triggers one rewrite, retry or abstention.
  \item Return answer text, citations, route trace, evidence metadata, backend metadata and verification result.
\end{enumerate}

\section{Data Sources}

The project will use public, open-licence, synthetic or self-created documents such as papers, technical documentation, generated reports, screenshots and slides. These will be used only where permitted and cited if they appear in the dissertation. The application may also process self-provided non-sensitive test files during development. Self-created screenshots and slides will avoid personal, confidential or copyrighted third-party content unless permission is clear.

The benchmark will contain public or synthetic multimodal documents and manually prepared question-answer pairs. Each item will include the query, expected route or route family, target modality, expected answer, accepted evidence references, and source identifiers such as file name, page, slide, table, figure, bounding box, element ID or graph community. Predictions will also record backend metadata so that local smoke backends are not confused with configured ColPali, VLM or LLM-planner backends. No private scraping, personal records, confidential documents or participant feedback are required.

\section{Testing and Evaluation}

Technical testing will cover controller schema validation, route selection, route executors, evidence bundle construction, retrieval evaluation, claim verification, citation construction, CLI commands, Web/CLI contract behaviour, knowledge graph services and benchmark metrics. Integration tests will check that a document or slide deck can be indexed, routed, retrieved, answered, verified and cited through the same runtime used by both Web and CLI.

The evaluation will use route-level ablations. The main comparison will include fixed text RAG, text RAG, at least one multimodal route, controller-auto routing, hybrid retrieval and CRAG-guarded execution. Other configured routes, such as page-image, element or graph-inspired routes, will be reported where their backends are available.

Metrics will combine several evaluation traditions. ALCE-style metrics will report fluency, correctness, citation precision/recall and attributable claim rate. MMDocRAG-style metrics will report page hit, element hit, image quote hit, cross-page evidence hit and multimodal answer support. RAGTruth-style metrics will report unsupported claim count, unsupported claim rate, contradiction count and abstention correctness. The benchmark will also report routing accuracy, retrieval recall@k/MRR, latency, backend type, cost where relevant, and qualitative error categories. The benchmark will adapt ALCE-, MMDocRAG- and RAGTruth-style metrics at prototype scale rather than attempting to reproduce the full external benchmarks.
